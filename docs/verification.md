## 系统接收耗时

2026-09-30，安装在 `/Applications` 的应用提交自身测试通知，由 macOS 正常投递。统计起点为提交通知，终点为 GUI 收到对应接收通道的结果；不包含飞书服务端和客户端提交前的等待，也不包含浮层排队时间。

数据库接收构建的五次结果为 5131、5132、5133、5165、5139 毫秒，中位数 5133 毫秒。只读系统日志同时记录了横幅在 14:00:30.229 出现、`usernoted` 在 14:00:35.233 执行延迟数据库写入，相差 5.004 秒。该等待发生在系统落库前。

横幅接收构建（可执行文件 SHA-256 前缀 `6ce05b9467b5`）同一条通知的两路结果：

| 次数 | 横幅接收 | 数据库读回 |
| --- | ---: | ---: |
| 1 | 311 毫秒 | 5142 毫秒 |
| 2 | 160 毫秒 | 5134 毫秒 |
| 3 | 143 毫秒 | 5136 毫秒 |
| 中位数（各三次） | 160 毫秒 | 5136 毫秒 |

续会话的中间构建（SHA-256 前缀 `77569054a1c4`）另一次系统测试为横幅 139 毫秒、数据库 5136 毫秒。该数据不代表最终构建的飞书端到端耗时。

结果说明横幅接收可避开本机约五秒的系统写入等待。样本只包含本应用测试通知，不作为飞书或全部应用的速度、覆盖率保证。

## 真实消息验收方法

先确认菜单的系统通知状态为「监听中」，再从常用应用各产生数条新通知，逐条记录系统是否出现、浮层是否出现、是否在所有屏幕出现、出现延迟及有无重复。分母应为本轮系统实际收到的通知数，不能把未发送成功的消息计算成工具漏收。批量突发、立即清除和通知更新分别测试。

在设置窗口点击「发送系统通知测试」，分别记录「横幅 … 毫秒」和「数据库 … 毫秒」，并目视核对浮层、通知时间及有无重复卡片。横幅测试需辅助功能已授权且本应用系统横幅开启，数据库测试需完全磁盘访问。耗时包含 macOS 投递和本工具调度，不包含排队后才展示的等待；不代表飞书消息在其服务端产生后的总延迟。连续测试时记录每次耗时和样本数，不只挑最快一次。普通通知的「打开应用」只需激活来源应用，不应再打开通知中心或定位消息。

Codex 验证需使用实际会触发审批的测试会话，并在原 CLI 中完成批准或拒绝；另行触发一条真实提问，确认回答后相应提醒清除。手动发送的样例 JSON 仅验证桥接与展示，不计为真实 Codex 事件验证。
